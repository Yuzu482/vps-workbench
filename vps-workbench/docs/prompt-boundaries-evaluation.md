# 提示词与输出边界评测计划

状态为待批准。以下 12 个样例各执行 A、B、C 三组，最多 36 次模型调用。超时、拒绝和格式失败均占一次额度。各组只提交一次，分支所需的上游回复、设计基线和已完成的记忆源轮次均由固定夹具提供。

## 对照设置

- A 组使用 `b58cc2d` 的原提示词，并在评测开始前记录对应 VPS 上的实际模型和推理设置。
- B 组仅换成本次提示词。VPS、账号、模型、档位、输入、附件、上游回复和设计基线与 A 相同。各组使用同一输出预算及同一验收器。
- C 组沿用 B，每个样例仅改变模型或推理档位之一。先在目标 VPS 的目录中核对候选模型和该档位。若候选需要同时改变两项，先记录单项对照，组合测试另行批准。

## 12 个固定样例

评测前将夹具的字节内容、校验值及预期结果写入同一份评测记录。下列字符串、顺序和基线在三组之间固定。

| --- | --- | --- | --- |
| 1 | 使用工作流长度回归夹具的八个阶段和空连线，将前七条指令各设为 700 个「证」，末条指令以 `😀` 开头，再用「据」补齐 JSON 正文至 5,800 个 UTF-16 单元。请求「给每个阶段补上证据位置的说明，返回完整草案」。 | 一个完整的 `vps-workflow` 块，围栏及换行合计不超过 8,192 单元，原有阶段和连线完整。 | Sol medium |
| 2 | 草案有 `write` 和 `review`，从 `write` 连向 `review`。指令分别为「写出初稿。」和「核对初稿。」。用户要求「给审校阶段增加证据位置」。 | 只改 `review.instruction`，保留工作流名、ID、执行端、模型、连线及本机配置。 | Sol low |

## 记录方式

先按格式、内容准确性、修改范围和画板可用性逐项验收。记录失败原因、缺失证据、使用的原始任务、画板数和有效跳转数。格式通过后的内容仍需对照冻结输入核验。

合格结果记录从发起请求到首个可见文本的耗时，以及到可解析、可审阅或可渲染结果的耗时。记忆任务另记录源回复结束到笔记写入并可检索的耗时。记录实际返回的模型、档位和输入、缓存、输出 token；每组总 token 与成本按通过验收的任务数计算，同时保留失败请求的用量。

公开费率估算只采用与实际模型 ID、计费类型和日期对应的公开费率。按计费口径分别用各 token 数乘以每百万 token 费率，再汇总到每个通过任务。订阅额度和未公开的内部成本单列，缺少适用费率时留空。实际质量、延迟、用量和成本尚未测量，本地回归只验证软件行为和请求边界。
